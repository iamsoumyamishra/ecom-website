# Checkout, payment and order operations

Checkout requires a verified email, a customer-owned cart, Stripe credentials, card-only payment-method configuration, explicit shipping countries/delivery price, and explicit tax treatment. Browser totals, prices, currencies and ownership claims are rejected by strict contracts. Prices are reloaded from published variants; quantities are bounded. A checkout has a client UUID idempotency key scoped to its owner and a request hash; changing input under the same key is a conflict.

The API locks the cart, blocks overlapping live attempts, updates stock conditionally in sorted variant order, claims any limited fixed-value discount and creates reservation/order/item/address snapshots in one PostgreSQL transaction. A cart with an active checkout is frozen until that attempt is terminal. Guest cart merge locks both carts in sorted order and bounds merged quantities to current availability.

Hosted Checkout creation runs outside that transaction using `checkout-{attemptId}` as the Stripe idempotency key. The request uses immutable snapshot line prices with exact discount-cent allocation, EUR, disabled adaptive pricing, a designated card-only payment configuration and stable order/attempt metadata. Returned payment-method types are checked; unexpected configurations are expired rather than offered to customers. `integration_identifier` is stable per attempt and includes eight generated letters, supported by Stripe 22.4.0's API types. An ambiguous network failure preserves reservations and is retried under the same key; a confirmed invalid request compensates reservations. Requests older than 23 hours with uncertain creation enter manual review before Stripe's idempotency retention can lapse.

Success/cancel redirects read authenticated API status. They do not prove payment or release stock. Stripe posts to `/api/webhooks/stripe` through the shop origin. Express raw bytes are preserved before JSON parsing and verified with the environment-specific signing secret. Receipt storage is durable and contains only event type and provider object ID, avoiding unnecessary customer/card data. HTTP success means receipt persisted; the dispatcher processes/retries it separately.

Reconciliation retrieves current Stripe objects instead of trusting stale event payloads. It checks session completion and paid status, exact EUR amount, order/attempt/session references and succeeded PaymentIntent/received amount. Under an attempt lock it records a unique payment, converts held stock to sold, finalizes discounts, marks the order paid, clears the frozen cart and adds a unique confirmation outbox row. Different events about one payment cannot sell stock twice. Email/Redis failure cannot roll back the payment transaction.

Open sessions are reconciled every dispatch cycle. Cleanup first retrieves or expires the provider session, then re-reads it. Only a terminal expired session releases stock. A racing late payment without held allocation records its payment ledger and sets REVIEW/HOLD, never silently fulfills it. Operations must investigate that audit record and refund or resolve allocation explicitly. The ledger remains authoritative for net revenue.

Staff can ship allocated paid/partially refunded, unfulfilled orders with a carrier and tracking reference. The shipment transition and notification intent are transactional and audited. Refunds reserve the refundable amount under a payment lock, require fresh staff verification, use `refund-{localRefundId}` with Stripe, and are confirmed/reconciled against provider objects. Partial refunds aggregate successful amounts without over-refunding. Ambiguous requests retain their local allocation and retry; old uncertain requests enter REVIEW. Refunds do not restock merchandise; record approved returns as explicit inventory movements with a reason.

Outbox intents remain PENDING until email provider acceptance. BullMQ uses stable row IDs, exponential retries and deduplication. Lost Redis queues can be rebuilt from PostgreSQL intent. The distributed scheduler has a 120-second Redis lease; handlers remain idempotent under overlapping lease expiry/retry. Provider email idempotency helps with ambiguous submission, but its retention window means exactly-once delivery is not promised. Pending receipts/notifications and review states need monitored operational alerts.

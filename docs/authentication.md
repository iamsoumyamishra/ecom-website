# Authentication and email

Better Auth 1.7.7 is pinned with its Prisma adapter and email OTP plugin. The supported Express `toNodeHandler` runs before body parsing. Two instances share the database while using exact shop/admin base URLs and separate host-only cookie prefixes. Only these routes are permitted:

| Method | Route                                       | Purpose                                           |
| ------ | ------------------------------------------- | ------------------------------------------------- |
| POST   | `/api/auth/email-otp/send-verification-otp` | `{email,type:"sign-in"}`; generic acknowledgement |
| POST   | `/api/auth/sign-in/email-otp`               | `{email,otp}`; consume OTP and set session cookie |
| GET    | `/api/auth/get-session`                     | Current session/user or null                      |
| POST   | `/api/auth/sign-out`                        | Revoke the session and clear cookies              |
| GET    | `/api/auth/ok`                              | Better Auth handler health                        |

Email is trimmed and lowercased without removing aliases. Codes are cryptographically generated by Better Auth, six digits, hashed in Verification, expire after 300 seconds, rotate on resend and allow five failed attempts. A unique verification identifier and Prisma adapter atomic consume support one-use concurrent verification. Redis atomically enforces a shared 60-second email cooldown and an IP window of 30 auth attempts per minute. The API also applies a shared request window. Redis failure prevents authentication rather than falling back to replica-local limits. Local Next proxy requests share an aggregate IP bucket; production Nginx forwards its actual peer IP.

Resend sends the React Email HTML and text template using server-only credentials. Domain setup requires the provider's verified SPF/DKIM records and a chosen DMARC policy. Use a controlled mailbox for manual test-mode validation. Automated tests replace only delivery transport and never send real mail.

**Version-specific delivery behavior:** Better Auth 1.7.7's `runInBackgroundOrAwait` catches callback exceptions. `await-submission.plugin.ts` uses the documented plugin init/context extension to await and propagate them. The callback also invalidates the stored challenge on submission failure. This behavior is covered by a handler regression test and must be reviewed on upgrades. Success means provider submission acceptance, not inbox delivery.

`cookie-only.plugin.ts` uses the response extension to remove session tokens, IPs and user agents from browser JSON while preserving cookies. Internal server session APIs keep the data needed by Better Auth. Sessions last seven days, update at most daily, use no cookie cache, and are revoked on logout or disabling staff access. Current role and disabled status are reloaded for every protected commerce call. Production cookies are Secure/HttpOnly/SameSite=Lax with no Domain attribute. Origin checking is explicitly enabled, including tests; commerce proxy mutations also validate the original Origin.

First verified customer sign-in creates CUSTOMER. Client-supplied role/disabled fields are not accepted as authority. Admin code requests succeed generically for non-members without sending mail; verification requires an existing enabled STAFF/OWNER. Public signup never grants staff privileges. Owner-only staff invitations/revocation and policy publishing, plus refund requests, require fresh sign-in within five minutes. The initial owner is bootstrapped by `pnpm admin:bootstrap email@example.com`, which refuses existing accounts/owners and creates an audit record. Stronger staff MFA is a launch-hardening follow-up.

References: [email OTP](https://better-auth.com/docs/plugins/email-otp), [Express handler](https://better-auth.com/docs/integrations/express), [plugin extensions](https://better-auth.com/docs/concepts/plugins), [Resend Node SDK](https://resend.com/docs/send-with-nodejs), [sender domain verification](https://resend.com/docs/dashboard/domains/introduction). Options and adapter consumption behavior were also checked against installed source.

Shared Redis limits cover both IP and normalized-email hashes (30 authentication requests per five-minute email window, plus the IP minute window). Verification failures use a generic invalid-or-expired response. Resend delivery failures remain explicit 503 responses.
